# Operations: the always-on Prism runtime (Strategy Lab Phase 14)

> **Exactly one runtime is permitted to write the live prospective Prism database.**
>
> **Moving hosts does not restart or alter any prospective research or paper-trading experiment.**

Phase 14 is infrastructure only. It changes where and when the existing commands run. It does
not change what they compute, record or send. No strategy, policy, cohort, execution model,
paper run, ledger, tracking, watch or evidence record was created, reset or altered by it.

## Architecture

```
Railway service "prism-runtime" (project "prism", always on)
  tini → supercronic (UTC crontab generated by `market ops crontab`)
       → `market ops cycle <job>` → existing CLI commands, in the existing order
  volume /data (authoritative):
     prism.duckdb                  the live database (claimed by railway-prism-runtime)
     raw/                          raw provider payloads (provenance archive)
     backups/{daily,weekly,manual} verified versioned backups
     logs/runtime.log              rotating, 5 × 5 MB
  → Telegram (co-pilot alerts, paper notifications, daily paper brief, infra alerts)

Home PC (non-authoritative)
  development and tests on scratch copies; read-only inspection of pulled backups;
  rollback launchers (forward_run.sh, oi_collect.sh, daily.sh) whose Windows tasks are disabled
```

**Why Railway.** The account already ran its always-on services there, and the CLI was
authenticated. It gives a single Linux container with a persistent volume, restart-on-exit,
retained logs, SSH (`railway ssh`), and volume file transfer (`railway volume files`). Railway
never mounts one volume into two deployments, and it stops the old container before starting
a new one when a volume is attached, so the platform enforces a single writer as well. The
workload (a few short Python runs a day) does not justify anything larger. No Kubernetes, no
queue, no networked database.

**Why supercronic.** There is no systemd in a container. supercronic is a small cron built for
containers: it logs to stdout and waits for running jobs on SIGTERM. Locking, failure state
and history are not left to it. They live in Prism (below).

## The single-writer rule

1. **Authority claim, in the database.** Migration 17 adds `runtime_events`. The newest
   `authority_claimed` event names the one runtime allowed to write the file. `Store` enforces
   the claim on every writable open:
   - unclaimed database (development, tests): unchanged behaviour;
   - claimed database: writable only with `PRISM_RUNTIME_ROLE=authoritative` and
     `PRISM_RUNTIME_ID` equal to the claimed id, or with `PRISM_RUNTIME_ROLE=scratch`, which
     says explicitly that the file is a copy you are deliberately modifying;
   - `PRISM_RUNTIME_ROLE=authoritative` never creates a database and never writes an
     unclaimed one.

   Reading is always allowed. A copied production database (for example a pulled backup on
   the laptop) is therefore **non-authoritative by default**: `market lab paper run`,
   `forward run`, `copilot run`, `brief --send` and so on exit 2 with "Refused (not the
   authoritative runtime)", before writing or sending anything. The role is neither a secret
   nor a trading switch. It governs only which machine writes this file.
2. **Runtime lock.** `market ops cycle` holds an exclusive `flock` on
   `/data/prism.duckdb.runtime.lock` for the whole job. A second job waits (scheduled:
   `--wait 3600`) or exits 75 (manual default `--wait 0`). The kernel releases the lock when
   the holder dies, so a crash never leaves a stale lock. DuckDB's own file lock still guards
   each open, and `PRISM_LOCK_TIMEOUT` (600 s) makes other processes wait, not fail.
3. **Jobs refuse to run off the runtime.** `market ops cycle` requires the authoritative role
   and an existing claimed database. On the home PC it exits 2.

## Schedule (UTC) and pipeline order

| job | times (UTC) | steps (existing commands, in order) |
|---|---|---|
| `prospective` | 00:10, 00:45, 03:00, 06:00, 11:00, 17:00 | `lab forward run` (Hyperliquid candles + funding + HL OI snapshot → Phase 8 check → resolve) → `lab copilot run --no-update` → `lab paper run` → `lab paper brief --send` (Phase 13 snapshot + brief) |
| `backup` | 01:30 | checkpoint → copy → verify → prune → record |
| `oi` | 02:30, 08:30, 14:30, 20:30 | `oi collect` (Binance OI backfill + HL OI snapshot) |
| `daily` | 09:00 | `update` → `scan` (the old 10:00 UK "Prism daily" task) |
| boot | 60 s after every container start | one `prospective` cycle (catch-up after restart, reboot or deploy) |

**Provider timing (checked 2026-10-04).** Hyperliquid's daily candle closes at 23:59:59.999 UTC
and is served immediately. Funding for an hour was published within minutes of the hour (the
17:00 UTC funding was present at 17:08). **00:10** is therefore the main run for bar T. The
later runs are retries, all inside the forward 1-day live window and the paper 12-hour entry
window: 00:45 and 03:00 for a late upstream bar, 06:00 and 11:00 as last chances inside the
entry window. 17:00 resolves late outcomes and keeps the longest gap between prospective runs
at 7 h 10 m, for the heartbeat. Every run after the first is a no-op when nothing is new. As
before, steps run even if an earlier one failed; the job fails if any step failed.

The schedule is defined once, in `market_signal.ops.runtime.SCHEDULE`.

## Data dependencies

| dataset | job | recoverable later? |
|---|---|---|
| Hyperliquid daily candles + funding | `prospective` (`forward run`) | yes, a backfill window. But a **prospective evaluation** missed outside its live window is never backfilled |
| Hyperliquid OI snapshots (`perp_snapshots`) | `prospective` and `oi` | **no**: capture-time snapshots, prospective-only. Now taken around the clock (~10/day), so the old overnight PC gap is gone |
| Binance OI 1h (`perp_oi_history`) | `oi` | yes: rolling backfill, ~30 days |
| spot/equity/macro (`update`) and `scan` | `daily` | yes |

A failed raw ingestion is not a missed prospective signal. It shows in the step's exit code
and in `market status` Data/OI, and the next run recovers it. The OI semantics, venue
separation and gap diagnostics are unchanged (docs/OPEN_INTEREST.md).

## Restart, crash and retry

- **Container restart / host reboot / deploy:** Railway restarts the container
  (`restartPolicyType: ALWAYS`). supercronic resumes the schedule, and the boot catch-up runs
  one prospective cycle.
- **Crash mid-cycle:** the `runtime_cycles` row stays `running` (visible in status). The lock
  is released by the kernel. The next run repeats the steps, and each step is idempotent
  (forward evaluations once per tracking/bar, co-pilot decisions once per policy/strategy/asset/bar,
  paper bars once per run with all events in one transaction, a brief once per paper day,
  notifications with unknown outcome never resent). No duplicate evaluations, alerts,
  orders/fills, funding or briefs.
- **Hung step:** killed after `PRISM_STEP_TIMEOUT` (45 min). The step is recorded as failed.
- **Telegram down:** delivery attempts fail and are recorded. Ledgers and evidence are
  unaffected (Phases 10, 12 and 13).
- **Provider down:** the update step fails, and the evaluations then see no new bar. Nothing
  is invented.

## Disk health

The thresholds are the free fraction of the volume: **warning < 15%**, **critical < 5%**.
These are infrastructure only, not trading policy.

- Warning: logged on every job; `market status` Disk = ATTENTION.
- Critical: the job does **not run** (exit 3), a "PRISM INFRA" Telegram alert is sent, and
  the heartbeat gets `/fail`. **Nothing is ever deleted** in response to low disk.
- A backup refuses to start unless the copy fits above the critical line.
- Logs cannot fill the disk: Railway retains stdout, and the file log rotates at 5 × 5 MB.

## Backups

- **When:** daily at 01:30 UTC (after the main cycle and its retry). A `manual` backup is
  taken before every deploy (`deploy.sh`) and on demand: `market ops backup --label <why>`.
- **How:** under the runtime lock: `CHECKPOINT`, then a byte copy while a read-only DuckDB
  connection keeps every writer out. The copy goes to `.part` and is fsynced and renamed, so
  there is never a half backup.
- **Verified every time:** the copy is opened read-only, and its schema version, paper run,
  ledger head, latest snapshot and every evidence-table digest must equal the live database
  at copy time. A `backup_verified` runtime event records the path, sha256 and size.
- **Retention:** daily 7, weekly 5 (a hard link to the daily copy, taken at most once per
  ~week), manual 6. Pruning touches only `backups/*/prism-*.duckdb` and never the live file.
  About 11 copies × ~135 MB.
- **Off-host copy:** `deploy/railway/pull_backup.sh` (home PC) downloads the newest daily
  backup, checks its sha256 against the server, and verifies it.
- **Restore rehearsal:** `market ops restore-test <backup>` copies to a temporary scratch dir,
  opens it writable as `scratch` (as a restore would), compares, and deletes it. Production is
  never the target of a test restore.

### Restore (real)

1. `railway ssh -- market ops backup --label pre-restore` (if the live file is readable).
2. Stop the schedule from writing: deploy is the simplest stop. Alternatively, run the restore
   inside the lock: `railway ssh` and then
   `flock /data/prism.duckdb.runtime.lock sh -c 'cp /data/backups/daily/<file> /data/prism.duckdb.restore && mv /data/prism.duckdb.restore /data/prism.duckdb'`.
3. `market ops preflight`, then `market ops continuity`, then `market status`.

Prospective cycles missed while the database was being restored are not backfilled.

## Health and inspection (read-only)

```
railway ssh --service prism-runtime -- market status          # all components + infra rows
railway ssh --service prism-runtime -- market ops preflight   # revision, role, claim, disk
railway ssh --service prism-runtime -- market lab paper status
railway ssh --service prism-runtime -- tail -n 200 /data/logs/runtime.log
railway logs --service prism-runtime                          # platform log stream
deploy/railway/pull_backup.sh && uv run market --db data/remote/<file> status   # local copy
```

`market status` keeps the strategy rows (Data, OI, Forward, Co-pilot, Paper) separate from the
infrastructure rows:

- **Runtime (infra):** the authoritative runtime and whether this process is it, the last
  successful prospective cycle, the next scheduled one, and each job's last result;
- **Backups (infra):** the latest verified backup;
- **Disk (infra);**
- **Telegram (infra):** delivery records in the last 24 h.

Run at home against a pulled copy, the Runtime row says the process is **not** the
authoritative runtime.

## External heartbeat

Prism's Telegram cannot report that Prism itself is down. There are three layers:

1. Railway restarts the container automatically, and emails the account owner when a deploy
   fails or crashes.
2. The daily paper brief arrives once per completed paper day. A missing brief is a visible
   human signal.
3. **Optional dead-man's switch:** set `PRISM_HEARTBEAT_URL` (for example a free
   healthchecks.io check, period 8 h, grace 1 h). Each prospective cycle pings it on success,
   or `<url>/fail` on failure or critical disk, and the external service alerts when the pings
   stop. **Not configured yet:** it needs an account the user creates. Until then, an outage of
   the Railway service itself is noticed only through layers 1 and 2.

## Deploying future commits

```
uv run pytest && uv run ruff check src tests dashboard && uv run ruff format --check src tests dashboard
git commit … && git push
deploy/railway/deploy.sh <commit>       # default HEAD; refuses uncommitted tracked changes
railway logs --service prism-runtime     # watch the build and the boot catch-up cycle
railway ssh --service prism-runtime -- market ops preflight
railway ssh --service prism-runtime -- market ops record-deploy --note "<what changed>"
railway ssh --service prism-runtime -- market status
```

`deploy.sh` records the server's current state and takes a verified **pre-deploy backup** on
the server. It then uploads `git archive <commit>` plus a `REVISION` file (never the working
tree, `data/` or `.env`) and lets Railway build the pinned image. Python 3.12.3 and every
package come from `uv.lock`; supercronic and uv are pinned by version and checksum. The old
container receives SIGTERM, and supercronic lets a running job finish (900 s drain). The new
container starts, and its boot cycle applies any migration on its first writable open and runs
a normal idempotent cycle.

- **Infrastructure-only changes** do not reset any experiment. Each run records its
  `software_id` as provenance, and the git commit comes from `REVISION` because the image has
  no `.git`.
- **Semantic changes** (compiler, vocabulary, evaluator, policies, engine) trip the existing
  version checks. For example, forward tracking notes "semantics changed since enrollment;
  not evaluated", and the paper engine refuses unreleased policy IDs. Such a change is a
  research decision, not a deploy.
- **Bad migration:** restore the pre-deploy backup (see Restore), then redeploy the previous
  commit with `deploy.sh <previous-commit>`.

## Secrets

The Railway service variables hold only what the jobs use: `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_CHAT_ID` (co-pilot/paper/brief/infra messages), and `TIINGO_API_KEY`, `FRED_API_KEY`,
`EIA_API_KEY`, `SEC_USER_AGENT` (the `daily` market update). They were set from `.env` through
stdin and never echoed. `.env` is not in the image (`git archive`), and nothing logs tokens: the
Telegram client never echoes its URL. `PRISM_RUNTIME_ROLE` and `PRISM_RUNTIME_ID` are plain
service variables, not baked into the image.

## Home PC role and rollback

The home PC is non-authoritative. The Windows tasks **Prism forward**, **Prism OI collect** and
**Prism daily** are **disabled, not deleted** (kept for rollback). Their wrappers remain in the
repo, and against the claimed database every write they attempt is refused anyway.

**Rollback to the home PC** (only if the server is lost):

1. Make sure the server cannot write: `railway down --service prism-runtime`, or delete the
   deployment in the dashboard.
2. Get the newest database: `deploy/railway/pull_backup.sh` (or the live file, via
   `railway volume files download`), and put it at `data/prism.duckdb`.
3. `PRISM_RUNTIME_ROLE=scratch uv run market ops claim-authority --runtime-id home-pc --supersede --reason "rollback: <why>"`
4. Add `PRISM_RUNTIME_ROLE=authoritative` and `PRISM_RUNTIME_ID=home-pc` to `.env`.
5. Re-enable the tasks: `schtasks.exe /Change /TN "Prism forward" /ENABLE`, and the same for
   "Prism OI collect" and "Prism daily".

Cutting over to a new host repeats the cutover below, with a superseding claim.

## Troubleshooting

| symptom | meaning / action |
|---|---|
| `Refused (not the authoritative runtime)` (exit 2) | writing a claimed DB from the wrong machine: use the server, or `PRISM_RUNTIME_ROLE=scratch` only on a copy |
| `ops cycle` exit 75 "skipped: another runtime job is running" | expected overlap; the scheduled one queues for up to 1 h |
| `ops cycle` exit 3 | disk critical: grow the Railway volume; nothing was deleted |
| Runtime row `STALE` | no successful prospective cycle for > 8 h: check `railway logs` / service status |
| a `running` row that never finished | a crash or kill mid-job; the next cycle retried it |
| preflight `ready_for_jobs: false` | role/id variables, missing `/data/prism.duckdb`, claim mismatch, or critical disk |
